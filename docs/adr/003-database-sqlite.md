# ADR-003：数据库选用 SQLite

- 状态：已采纳
- 日期：第 3 周
- 关联：六张表 DDL（`docs/er.md`）；单机课程部署

## 背景

设备云监 v1 运行在学生本机：一台 Modbus 模拟从站、一个后端进程、一个前端开发服。需要持久化设备台账、遥测时序、报警、工单与备件数据。课程强调「零安装/少运维、单文件可拷贝、可验收」，同时预留将来数据量或并发上升时的升级路径。

## 决策

采用 **SQLite** 作为 v1 唯一业务数据库（单文件 `.db`）；访问可用 SQLAlchemy 或原生 `sqlite3`。表结构严格按 `01` 第六节，不另建审计库。

## 理由

1. **零服务进程**：无需单独安装/启动 PostgreSQL/MySQL，降低第 1 周环境失败率。  
2. **单文件便于交作业与演示**：拷贝 `.db` 即可带走数据；与 Docker 一键演示也简单。  
3. **足够支撑课程负载**：单采集写者 + 少量页面查询；配合 `(device_id, ts)`、`alarm(ts)` 索引可满足课内曲线与列表。

## 代价

1. **并发写能力弱**：多进程同时写同一库易锁等待；若将来「多用户同时关单/录入」，需要升级 PostgreSQL 或改为单写者队列。  
2. **网络访问与权限模型简单**：不适合直接当「中心库」给多台机器同时连；多机部署要迁出 SQLite。  
3. **运维特性有限**：细粒度角色权限、复杂复制、部分高级 SQL 能力弱于主流服务端数据库。

## 备选方案及未采纳原因

| 备选 | 未采纳原因 |
|------|------------|
| PostgreSQL | 功能强，但本课 v1 单机无并发写刚需；安装/服务管理增加环境成本，违背「零安装优先」。 |
| MySQL / MariaDB | 同上，额外套件与端口管理；课程收益不明显。 |
| 仅内存字典/JSON 文件 | 难支撑遥测历史与关联查询，不利于第 5–6 周按表实现业务。 |

## 升级触发条件（何时放弃 SQLite）

出现以下任一情况再迁 PostgreSQL（迁库时尽量保持表名/字段与 `er.md` 一致）：

- 需要多用户同时写入且出现明显 database is locked；  
- 需要多机共享同一库；  
- 遥测数据量增大到单文件备份/查询明显卡顿，且索引优化无效。
